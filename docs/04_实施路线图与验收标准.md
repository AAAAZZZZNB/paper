# 实施路线图与验收标准

## 1. 阶段规划

### 阶段 0：产品与数据准备（1 周）

- 固化产品需求、角色、字段和数据脱敏方案。
- 整理论文已有事故数据、轨迹数据、模型结果和案例资料。
- 建立数据版本、模型版本和知识版本命名规则。
- 用 3~5 个代表性事件建立端到端样例。

### 阶段 1：研究结果可视化 MVP（2~3 周）

- 事故数据上传和质量报告。
- SHAP 任务运行、图表展示和结果导出。
- 轨迹冲突指标、POT/EVT 分析和阈值展示。
- 基础事件详情页。

### 阶段 2：知识图谱与案例知识库（2 周）

- 实体/关系/规则数据结构。
- 图谱浏览和场景子图查询。
- 案例标签、案例页面和显式链接。
- 知识审核、发布和废弃流程。

### 阶段 3：风险 Agent 与报告草案（2~3 周）

- 事件解析器、阈值规则引擎和证据包。
- 图谱/案例检索工具。
- LLM 提示词模板、固定报告结构和输出校验。
- 报告草案、人工审核、导出和版本对比。

### 阶段 4：道路管理闭环（3~4 周）

- 风险地图和告警中心。
- 事件工单、责任分派、处置清单和超时升级。
- 处置反馈、复盘和知识更新建议。
- 模型/知识/规则版本与运行监控。

### 阶段 5：准实时与效果评估（持续迭代）

- 轨迹流接入和实时/准实时告警。
- 告警准确率、提前量和误报率评估。
- 处置措施效果评估。
- 多路段和多区域扩展。

## 2. MVP 端到端验收场景

### 场景 A：事故 SHAP

1. 用户上传事故数据。
2. 系统检查字段、缺失率和异常值。
3. 用户选择目标变量和模型参数，创建训练任务。
4. 系统生成模型指标和 SHAP 图。
5. 用户打开“夜间”或“暴雨”等因素的解释详情。
6. 用户将结果保存为知识候选并提交审核。

**通过标准**：任务可复现，图表可下载，知识候选可追溯到数据和模型版本。

### 场景 B：轨迹 EVT

1. 用户上传轨迹数据和道路场景信息。
2. 系统完成轨迹质量检查和冲突指标计算。
3. 用户选择 TDTC，设置 POT 阈值并运行模型。
4. 系统展示拟合结果、置信区间、重现水平和阈值建议。
5. 审核员发布一条高风险规则。

**通过标准**：模型失败有明确原因；阈值发布前必须经过审核；发布后可被事件规则调用。

### 场景 C：事件风险分析

1. 用户创建“暴雨 + 夜间 + 长下坡 + TDTC 低于阈值”的事件。
2. 系统独立执行规则判定。
3. 系统返回图谱证据和相似案例。
4. LLM 生成结构化风险报告和处置建议。
5. 一致性校验器检查事实、等级和证据。
6. 审核员修改并发布报告草案。

**通过标准**：报告包含风险等级、原因、阈值、案例、处置和待核验信息；高风险规则触发时报告不得降级；每条关键结论有来源或推断标记。

## 3. 质量门禁

### 数据门禁

- 必填字段完整率达到任务要求。
- 时间、坐标、车辆 ID 和道路 ID 通过一致性检查。
- 敏感字段已脱敏。
- 数据版本冻结后不可被静默覆盖。

### 模型门禁

- 训练任务保存随机种子和配置。
- 模型指标达到设定下限，或明确标记为“仅研究，不发布”。
- SHAP/EVT 结果能定位到具体数据和模型版本。
- 阈值必须通过稳定性和样本量检查。

### 知识门禁

- 实体名称符合规范词表。
- 关系方向和数值单位明确。
- 规则与知识条目不能互相矛盾；矛盾项必须进入人工审核。
- 仅已发布知识可供生产 Agent 使用。

### LLM 门禁

- 输出符合固定 JSON/结构化模板。
- 风险等级不低于规则底线。
- 未知信息明确标注。
- 历史案例内容有明确“案例参考”边界。
- 未支持事实率和证据覆盖率达到设定门槛，否则只能进入待审核状态。

## 4. 研发交付物

- 产品需求文档
- 系统架构和模块说明
- 数据字典和接口文档
- 样例数据与脱敏说明
- SHAP 分析任务和图表
- EVT 分析任务和阈值规则
- 知识图谱和案例知识库初版
- Agent 提示词、工具和校验器
- 风险报告模板
- 测试报告和验收记录
- 部署与运维说明

## 5. 首批测试数据建议

- 事故数据：选择能够覆盖天气、时段、道路类型、车辆类型和事故严重程度的脱敏样本。
- 轨迹数据：选择至少包含正常跟驰、急减速、追尾冲突和合流冲突的路段样本。
- 案例数据：先录入 10~20 篇结构化历史事故案例，统一 tags 和实体名称。
- 事件样例：准备低、中、高、极高四个风险等级场景，并包含缺失字段场景。

## 6. 关键风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 数据样本不足 | 模型不稳定、阈值不可靠 | 显示样本量和置信信息，不自动发布 |
| SHAP 被误解为因果 | 造成错误管理决策 | 界面固定显示解释边界，知识类型标记为模型关联 |
| EVT 阈值迁移失效 | 跨路段误报/漏报 | 绑定适用道路和时间范围，支持重新校准 |
| LLM 生成未支持事实 | 报告失真 | 证据包、事实允许集合、输出校验和人工审核 |
| 告警过多 | 值班人员疲劳 | 告警去重、合并、抑制和分级升级 |
| 自动措施风险 | 误封道或误限速 | P0/P1 只生成建议，不自动执行 |
| 知识过期 | 研判依据失效 | 有效期、版本和废弃机制 |

## 7. 建议的第一步

先不要直接开发全部功能。建议先用论文已有数据完成一个可演示闭环：

```text
一个事故数据集
  → 一张 SHAP 图
  → 一组轨迹 EVT 阈值
  → 一个风险知识子图
  → 一个危险场景事件
  → 一份带证据和处置建议的报告草案
```

该闭环跑通后，再增加地图、告警、工单和准实时接入，能够减少早期系统过度设计风险。
